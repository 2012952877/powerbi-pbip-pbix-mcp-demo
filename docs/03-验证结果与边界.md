# 验证结果与边界

> 公开版说明：保留原技术叙事与合成场景观察，部署定位参数已改为占位符。内部任务、身份、部署及截图来源回执不随仓库发布；公开成品与经过字段精简的 verification 见 [examples](../examples/README.md)。请先用自己的获准环境参数替换占位符。

如果你想把已有 PBIX 变为可编辑、可版本管理的工程，或把上游 PBIP 交付为 PBIX，可以从这套双向服务开始评估。最接近现有能力的输入是：**带本地模型的受信任 PBIX，或一个入口、包内完整报表与本地模型的 PBIP**；数据条件可控，并使用已适配的标准视觉对象。普通用户从公网 HTTPS 以个人身份登录，管理员负责私网节点、已连接解锁的 Windows 桌面和串行 worker。

下面沿实际输入变化解释发生了什么、为何如此，以及换成自己的工程后应验收什么。完整机制见[主指南](01-完整方案与实操指南.md)，网页登录和管理员恢复分别见[运行手册](02-日常复跑与运维.md)。当前是同一安全域内的受控多人试用；企业 SSO、恶意输入沙箱和跨客户操作系统隔离不属于已有授权能力。

## 1. 基本销售：从 PBIX 导出，再转回成品

基线工程的 `Sales` 表只有三行：A=10、B=20、C=30。模型中的 `Total Amount = SUM(Sales[Amount])` 计算总金额，报表卡片引用该度量值。没有筛选时应显示 **60**。

正向基线先从 `Synthetic.zip` 生成 PBIX：worker 打开工作副本，刷新精确匹配的内置数据，另存后关闭源进程，再以新进程打开成品。卡片 60 把数据、计算与绑定连到实际文件。

以这份 PBIX 为输入选择 **portable**，Desktop 又将它另存成完整 PBIP。导出的工程只携带本任务生成的非空模型缓存，不从其他任务补数据；在独立副本中重新打开工程后仍显示 60。再提交该 ZIP 转回 PBIX，新成品的独立 Desktop 进程仍显示 60。离线回转成立的条件，是工程实际携带了该模型所需的缓存，而不是把 ZIP 改成了另一种后缀。

重新打开很重要：原窗口能显示 60，可能只是它仍持有工程的内存状态；新进程必须从输出 PBIX 恢复内容。文件长度与 SHA-256 则解决另一个问题——确认客户端取回的正是远端产物，不负责判断业务口径。

可以对照[portable 工程](../examples/Sales-portable-c268.pbip.zip)与[往返 PBIX](../examples/Sales-roundtrip-5a09.pbix)，模式、输入摘要和复开结果见[公开示例索引](../examples/README.md)。接入自己的工程时，应预先定义总金额、行数或关键筛选后的结果；样例的 60 不代表所有 DAX 与数据行都自动得到等价保证。

## 2. 同一个 PBIX，导出定义与导出数据是两种需求

从原销售 PBIX 选择默认 **definitions**，导出包仍包含模型、报表和页面定义，但没有 `cache.abf`，也没有本机设置。独立 Desktop 进程可以打开这些定义；这个结果回答“工程是否可编辑”，不回答“脱离数据源是否仍能看到全部数值”。

| 目的 | 模式与已有行为 | 对自己的工程意味着什么 |
|---|---|---|
| 代码审阅、修改模型与页面、版本管理 | definitions，保留定义且不带模型缓存 | 另行安排数据加载；对外分享前仍需审查定义 |
| 保留既有数据、离线打开或回转 | portable，当前任务非空缓存随工程交付 | 缓存按原文件敏感级别管理；缺缓存明确失败 |
| 将一般 PBIP 转成含模型 PBIX | 使用输入已有缓存，非内置工程不自动刷新 | 没缓存会遇到 `DATA_CACHE_REQUIRED`；先在批准 Desktop 环境处理数据 |

定义不是纯粹无数据的目录。Sales 的三行数据写在 M 表达式中；即使删除缓存，这段内嵌内容仍在。真实工程还可能在查询、参数或模型文本中保留连接信息和敏感内容。所以 `contains_data=false` 只说明没有缓存/二进制模型，不代表“没有敏感数据”或“已经脱敏”。definitions 的 `data_values_verified=false` 表示这里检查的是定义，数据加载与业务数值仍由调用者按自己的工程确认。

[definitions 工程](../examples/Sales-definitions-rc4.pbip.zip)与[检查记录](../examples/Sales-definitions-rc4-verification.json)可供对照；也可解开 portable ZIP 查看其缓存与定义。自己的外部源认证、刷新权限和网络条件不会随一个工程 ZIP 自动配置好。

## 3. 多页、中文与关系：往返后检查结构与计算

只有一个卡片，无法发现第二页丢失、中文名称改变或表关系未生效。扩展工程 `Rich.zip` 因而保留同一份销售数据，增加产品维度和权重，并在两个页面使用卡片、分类柱形图和表格，共 5 个视觉对象。

| 类别 | 金额 | 关联权重 | 加权贡献 |
|---|---:|---:|---:|
| A | 10 | 2 | 20 |
| B | 20 | 3 | 60 |
| C | 30 | 4 | 120 |
| 合计 | 60 | — | 200 |

`Sales.Category` 通过关系连接 `产品 维度`；DAX 的 `RELATED` 取得权重，`SUMX` 将每行金额乘权重后相加。60 检查基本聚合，**200** 让关系与逐行计算进入观察范围。Rich 从 PBIP 生成 PBIX，再导出 portable PBIP 并转回 PBIX；最后的新进程仍保留两页、5 个视觉对象、总金额 60，两个页面均读到加权金额 200。中文、空格与 Ω 也位于入口、模型对象及文件名称中。

查看[portable 工程](../examples/Rich-portable-1b49.pbip.zip)、[往返成品](../examples/Rich-roundtrip-rc4.pbix)及[复开回执](../examples/Rich-roundtrip-rc4-verification.json)。[正向概览画面](bidirectional/assets/03-rich-overview-60-200.png)和[正向明细画面](bidirectional/assets/04-rich-detail-60-200.png)用于读懂这套结构：先看页签，再对应 10/20/30、20/60/120 与 60/200；回转结果则按自己的新成品逐页验收。

这些结果适用于样例中的简单关系和标准视觉对象。对象名称支持中文，与 Desktop 菜单语言适配是两回事：运行环境使用英文 UI、Desktop `2.157.1354.0`。复杂筛选、按用户限制可见数据的 RLS（行级安全）、复合模型或不同菜单语言，需要另选能揭示相应行为的工程来评估。

## 4. 多人工作台：同一身份可换入口，不能换成别人的权限

两个独立用户通过真实登录表单建立各自会话，一人选择完整工程文件夹，另一人选择 ZIP。两种输入都进入同一队列，各自的“我的任务”仅显示本人的记录。文件夹路径逐项受检查；孤立 `.pbip` 在页面中被提示补全工程，未被提交为转换任务。

其中的文件夹任务实际完成 Desktop 保存和新进程复开，随后从网页取回 PBIX 与检查记录。同一用户再经 HTTP MCP 下载，取得的文件内容与网页下载一致；这是同一任务的两种访问方式，不是网页做一份、MCP 另做一份。另一个用户在任务仍排队时取消成功，没有进入 GUI 转换，因此“已取消”不属于成功成品。

跨用户读取、取消与下载均被服务端拒绝；任务完成、产物已经可用后，再次跨用户下载也仍被拒绝。知道 ID 或改请求参数不会取得他人文件。HTTP 以 `JOB_NOT_FOUND` 拒绝；MCP 传输可能仍返回 HTTP 200，但工具结果是 `isError`、`ok=false`，表示请求已送达而受保护操作被拒绝。原始身份验收请求不公开；授权实现与可重复本地覆盖见 [portal](../src/pbip_mcp/portal.py) 和[测试](../tests/test_portal.py)，不把单元测试当成新的公网任务。

这项能力是应用层所有权控制。浏览器用个人凭证换取 Cookie，变更请求带 CSRF；HTTP MCP 用同一人的 Bearer 凭证。它不是企业单点登录，也没有将不同用户的 Desktop 分到独立 Windows 账户。受信同事可以排队共用节点；不同客户或不可信输入必须另评估独立 worker、存储、网络和操作系统隔离。

**公网链路进一步把网页操作与程序接入接在同一份文件上。** 普通用户通过 HTTPS 网页提交完整销售工程，Desktop 保存 PBIX 后在新进程显示 60，再从公网下载。随后同一用户经公网 HTTP MCP 提交这份确切 PBIX，选择 portable；反向保存不刷新数据，新进程打开工程仍显示 60。所得工程含本任务缓存、无本机设置，网页与 MCP 分别下载后文件相同。

这条路径说明公网网关能够传递真实上传、任务查询与双向成品，终点是 PBIP → PBIX → portable PBIP。前文销售与 Rich 的完整回转 PBIX 场景则回答离线工程再交付的问题，两类场景关注不同环节。[正向复开](../examples/Public-HTTPS-Synthetic-forward-verification.json)、[反向复开](../examples/Public-HTTPS-Synthetic-reverse-verification.json)与[portable 成品](../examples/Public-HTTPS-Synthetic-portable.pbip.zip)可供深入查阅。

公网可达也没有绕过网络与身份约束：App Service 在 HTTPS 入口接收流量，经专用 VNet 子网访问 VM 私网端口，NSG 与 Windows Firewall 限定后端来源。匿名请求返回 401，错误 Origin 或缺 CSRF 返回 403；Cookie 使用 Secure、HttpOnly、SameSite=Strict。HSTS/CSP 和 HTTPS 重定向保护浏览器入口，但不代替文件所有权与工程信任审查。可复用配置见[网关部署](../deploy/public-gateway/README.md)，本地接口覆盖见[公网边界测试](../tests/test_public_portal.py)。

## 5. 错误工程：先检查包装，再由 Desktop 解释定义

输入先过身份、格式、大小与路径检查，再进入 Desktop 加载。ZIP 要有唯一完整工程；PBIX 要是支持的本地模型容器，损坏、未知或不支持的连接模式会拒绝。数据模式和缓存也有前置条件。包检查控制文件进入工作目录的方式，Desktop 则处理模型语言、版本和实际加载；两者都不是任意 M 查询的沙箱。

| 遇到的输入问题 | 处理结果 | 对提交者的含义 |
|---|---|---|
| 非 ZIP 内容 | `INVALID_ZIP` | 先生成有效压缩包 |
| 缺报表或模型、存在多个入口 | `INCOMPLETE_PROJECT` / `AMBIGUOUS_PROJECT` | 提供唯一入口及完整相对引用，不让服务猜选工程 |
| 路径穿越 | `UNSAFE_ARCHIVE_PATH` | 重新打包，所有成员必须留在工程范围内 |
| 压缩比或声明成员尺寸超限 | `ZIP_BOMB` / `ARCHIVE_MEMBER_SIZE` | 检查内容及服务限额，不通过关闭限制来接收异常包 |
| 内置样例内容被修改 | `synthetic_fixture=false` | 修改后的查询与模型需要重新审查，不再继承自动刷新资格 |
| 非内置 PBIP 缺少缓存 | `DATA_CACHE_REQUIRED` | 先在批准 Desktop 中处理数据加载，不要求转换器执行任意刷新 |
| portable 导出未得到非空本任务缓存 | `PORTABLE_CACHE_MISSING` | 无离线成品，不从其他任务取缓存补齐 |
| 不支持的 PBIX、保护或 Desktop 提示 | 格式/保护相关拒绝或明确任务失败 | 保留标签与安全要求，由有权人员判断，不自动移除保护 |

保留的正向诊断场景还说明完整包可能含无效定义。TMDL 是模型文本语言；样例在 `model.tmdl` 中加入位置不合法、带缩进的 `ref table InvalidSyntax`，进入 Desktop 后报告 `UnsupportedObjectType`，即当前上下文不支持 `table` 属性。任务以 `DESKTOP_DIALOG_UNSUPPORTED` 结束，无成功产物，随后 worker 回到 ready/idle。现版本还要求非内置工程带缓存，直接重提这份无缓存坏定义会先遇缓存拒绝；该历史诊断用于解释解析层，而非承诺当前请求必然到达同一弹窗。

对外错误码说明 worker 遇到了不能继续处理的 Desktop 对话框，具体 TMDL 根因来自 UI Automation（读取窗口控件与文本的接口）取得的错误文本。遇到同一通用码时，应先读自己任务的诊断，不能一律归因于 TMDL。历史原始诊断不公开；定义位置和错误机制见[完整指南第 6 章](01-完整方案与实操指南.md)。

自动刷新限制也在这里发挥作用。PBIP 的 M 查询可以连接外部系统，包结构合法并不代表查询已获得执行授权。当前只有逐文件精确匹配的内置样例可以自动刷新；自己的工程即便只有一处修改，也要重新评估数据加载条件。

## 6. 连续任务、断线与到期：状态和文件分别恢复

连续运行时，多个请求可以先进入队列，但一个 worker 只操作一个 Desktop 任务。批量场景中，B 在 A 完成前已入队，直到 A 完成后才开始执行；A 的基本销售与 B 的多页工程分别生成成品。由此可见，排队使调用者不用争抢桌面，代价是后续请求必须等待前一项完成。

同一批中的 C 原本也应转换成功，却因交互会话丢失以 `INTERACTIVE_SESSION_LOST` 失败，未产生成功文件。历史批量结果因此返回整批 `ok=false`，同时保留 A/B 的成功结果。批量调用不具备全批回滚语义；使用者必须逐项处理结果。

恢复桌面连接、SSH 通道及 worker 后，新提交的基线任务完成保存、新进程复开和下载，卡片重新显示 60。旧 C 仍可从新的 controller 连接中查到 failed，且不能下载产物。恢复意味着**运行前提修复后，新任务可以继续工作**，而不是重写旧任务的结果或从它的保存中点续跑。这段历史观察用于说明恢复语义，原始运行回执未公开。

另外几种中断要分别处理：

| 当前情况 | 状态或接口行为 | 应采取的动作 |
|---|---|---|
| worker 离线 | 状态返回 ready=false，一站式 convert 拒绝执行 | 恢复桌面并 Start；显式 submit 虽能入队，仍需 worker 执行 |
| 任务仍 queued | 可取消，取消后无产物 | 不再需要时取消；领取后取消可能被拒绝 |
| controller 连接重新建立 | 能查询先前任务的持久状态 | 持有原任务 ID 查询，不因连接变化重复提交 |
| 本机目标文件已存在 | `CLIENT_OUTPUT_EXISTS`，原文件保持不变 | 选择新文件名 |
| 原任务已 succeeded，下载未完成 | 接口允许按原 ID 分别下载 PBIX 与 verification | 恢复通道后重新取回，不再消耗一次桌面转换 |
| 浏览器退出、会话到期或换了客户端 | 同一身份可以重新列出自己的持久任务 | 重新登录或用个人 HTTP MCP，不重复提交 |
| 产物经到期维护清理 | 历史状态保留，`artifact_status=expired`，下载明确过期 | 依据原输入重新申请，以新任务取得新产物，旧记录继续保留 |

表中的下载恢复是接口提供的操作路径；断线场景实际覆盖的是交互会话丢失后的失败保留与新任务恢复。人为终止 worker、在不同保存阶段崩溃后的进程清理和长期稳定性，还需要单独评估，不能用一次连接恢复代替。

留存维护只处理有期限的新任务，默认终态后保留 24 小时，并由管理员显式、有限量执行。它保留数据库历史和维护审计，不删旧原件或迁移前 legacy 任务；活动任务与持续 HTTP/MCP 下载由状态和租约保护。到期维护并不意味着后台会自动腾空整个目录。管理员需要同时管理预算、下载中的文件、异常遗留租约和归档责任。

持久 portal 解决的是“管理员本机 SSH 断开后入口不应随之退出”：具名任务运行于专用用户的 Interactive + Limited 会话，在该用户登录时触发。它仍不是开机就无需登录的服务；worker 还要求 RDP Active、桌面解锁。当前 VM 自动关机关闭，适合持续试用但增加保留成本，也不会消除登录、健康与值守责任。

## 7. 将自己的工程纳入范围前，先改变验收问题

现有结果适合支持受控试点。输入越偏离自包含小工程，越需要把“能保存”扩展成针对实际模型、数据和使用方式的验收。

| 新条件 | 为什么会改变结论 | 接入前应明确什么 |
|---|---|---|
| 外部文件、数据库或连接器 | 保存定义不等于数据可读取或刷新 | 网络可达性、连接器版本、身份与凭据、参数、隐私级别、刷新授权及缓存 |
| 复杂 DAX、RLS、增量刷新、复合模型、Direct Lake | 60/200 只覆盖简单聚合与一条关系 | 关键计算、筛选上下文、角色权限和各存储模式的验收方式；部分结构可能超出当前本地模型契约 |
| 自定义视觉对象、地图、外部图片、复杂书签与主题 | 页数和视觉数量相同仍可能有显示或交互差异 | 依赖安装、外部资源访问、逐页显示及交互检查 |
| 其他 Desktop 版本或中文 UI | 文件格式、控件和对话框可能变化 | 在批准版本中重新检查打开、保存、复开和错误处理 |
| 大工程、长任务或高并发 | 当前限额和串行桌面决定等待与存储压力 | 容量、超时、留存和使用窗口；不能直接扩大参数后承诺吞吐量 |
| 多用户扩大到多租户/跨客户 | 已有个人任务授权，但共享 Windows 账户不构成 OS 隔离 | 独立节点/部署、存储、出站网络、留存及诊断权限，不能直接公用一个 worker |
| 企业组织登录或扩大公网使用 | 已有 HTTPS 网关和个人授权，不等于组织 SSO 或生产服务级别 | 组织认证与可信身份映射、凭证生命周期、访问审计、容量及网关/桌面支持责任 |
| 受标签保护、加密或未知 PBIX | Desktop/PBIP 的格式与保护条件不能被自动化消除 | 按厂商规则决定能否处理，不移除标签或自动接受提示 |
| 世纪互联部署、在线发布、Copilot 或嵌入 | 现有环境是全球 Azure VM 中的 Desktop 本地保存 | 目标云的功能、端点、身份、许可证与在线链路需要分别确认 |

如果输入差异大、任务不多且经常需要人处理数据源提示，Desktop 人工另存为通常是更直接的基线。如果终点只是在线报表，Fabric 定义部署或 Embedded Report Authoring 可能减少中间步骤。具体输入、输出与运维取舍见[完整指南第 9—10 章](01-完整方案与实操指南.md)。
